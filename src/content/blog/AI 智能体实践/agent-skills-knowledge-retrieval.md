## 一、背景与动机

### 传统 RAG 的痛点

传统的 RAG（Retrieval-Augmented Generation）方案采用 **分块（Chunking）+ 向量嵌入（Embedding）** 的模式，虽然最终能调教出不错的效果，但调教过程非常痛苦，是一种"妥协模式"。

### 行业观点

LlamaIndex 创始人在 Twitter 上表达了类似观点：

> RAG 本身没有死，但固定的 Chunk + Embedding 模式应该已经死了。如果 Agent 可以动态地扩展周围文件的上下文，那么过多地考虑数据块的大小就没有意义了。

### Skill 的启发

Agent Skills 的**渐进式披露策略**（Progressive Disclosure）与上述理念高度契合：既能节省大量上下文，又能精准响应用户需求。

---

## 二、Skill 知识检索方案简介

借鉴 Skill 的设计模式，实现一个**专用于知识检索的 Skill**，核心目标：

| 能力 | 说明 |
|------|------|
| 指定目录检索 | 能在指定目录中检索关心的问题 |
| 跨格式联合查询 | 支持 Markdown、PDF、Excel 等多种格式，根据文件类型选择适合的读取方式 |
| 渐进式检索 | 先按关键词逐步缩小范围，再精准打开少量相关文件，避免无意义的 token 消耗 |
| 上下文整合 | 不简单给出命中行，而是结合上下文拼接可读的成段回答 |
| 多轮查找 | 支持在复杂问题上进行多轮查找和总结 |

## 三、演示效果

### 知识库结构

示例知识库包含多个领域的数据，文件格式多样：

```text
knowledge-base/
├── financial/          # 上市公司财报（PDF）
├── ecommerce/          # 电商订单数据（Excel）
│   ├── customers.xlsx
│   ├── orders.xlsx
│   └── data_structure.md   # 目录索引文件
├── ai-research/        # AI 领域行业资料（PDF）
└── security/           # 安全领域专业知识（Markdown/TXT）
```

### 测试场景

#### 场景一：金融领域 - PDF 检索

**问题**：三一重工前三大股东是谁？

**检索过程**：
1. 找到 Skill，读取知识库目录
2. 识别到财报数据为 PDF 格式
3. 读取 PDF 处理的 Reference 文档
4. 将 PDF 转换为 TXT
5. 根据关键词分段检索
6. 给出准确答案

#### 场景二：连续追问

**问题**：三一重工母公司的副代表情况如何？

- 因为 PDF 已在上一轮转换完成，检索速度更快

#### 场景三：电商领域 - Excel 跨表查询

**问题**：郑雪买了啥？

**检索过程**：
1. 读取 Excel 处理的 Reference 文档
2. 在顾客表中找到"郑雪"对应的 ID
3. 在订单表中根据用户 ID 找到购买商品
4. 准确回答：蓝牙耳机

#### 场景四：复杂查询

**问题**：有哪些用户买了儿童绘本？在什么时间？

- AI 快速完成多表关联查询并给出结果

## 四、实现原理

### 核心流程

```text
用户提问 → 定位领域 → 定位文件 → 读取分析 → 总结回答
```

#### 第一步：定位领域

分析用户问题，结合目录索引，定位知识可能存在的文件夹。

#### 第二步：定位文件

使用 `grep` 等命令在指定目录中检索，筛选可能相关的文件。

#### 第三步：按类型读取分析

| 文件类型 | 处理策略 |
|----------|----------|
| Markdown | 直接定位到匹配段落，结合上下文分析 |
| PDF | 编写代码将 PDF 解析为纯文本，按页/章节提取内容 |
| Excel | 编写代码读取分析，只看与问题相关的表、行、列 |

#### 第四步：总结回答

将检索到的知识整合，给出可读的成段回答。

### 关键设计原则

**1. 渐进式检索（尽量少读，但读得准确）**
- 优先查找最可能有答案的文件
- 仅读取相关行，必要时再扩展范围
- 避免无意义的 token 消耗

**2. 保持简单可控**
- 用户只需告知知识库位置
- 其余检索策略由 Skill 自动完成

### 关键技巧

**1. 文件夹按领域划分**

每个文件夹只包含特定领域下的文件（如金融数据、电商数据）。

**2. 目录索引文件**

每个文件夹下放置 `data_structure.md`，描述每个文件的用途。如果文件命名不规范且包含 PDF 等非纯文本格式，这是必要的。

**3. 渐进式披露**

多级嵌套领域时，AI 找到领域后才会读取该领域的目录索引，进一步节省 token。

## 五、Skill 目录结构

```text
knowledge-retrieval-skill/
├── skill.md            # 使用说明书
│                       # - 如何找本地知识库
│                       # - 如何根据目录索引逐层检索
│                       # - 不同文件类型的处理方式
│                       # - 最终回答风格
├── reference/          # 参考文档
│   ├── pdf-handling.md # PDF 解析方法
│   └── excel-handling.md # Excel 处理方法
└── scripts/            # 可执行脚本
    ├── pdf-parser.py   # PDF 解析脚本
    └── pdf-to-image.py # PDF 转图片脚本
```

**设计要点**：
- Reference 只在确定需要处理特定格式时才加载，节省 token 和注意力
- Script 放置 PDF 转换等特殊处理脚本
- 新增格式时，扩展 Reference 或 Script 即可

## 六、方案对比

### 与传统 RAG 的区别

| 维度 | 传统 RAG | Skill 知识检索 |
|------|----------|----------------|
| 基础设施 | 需要向量数据库 | 不需要，基于本地目录 |
| 检索方式 | 向量匹配内容，大模型只做总结 | 大模型参与分词、上下文匹配和决策 |
| 灵活性 | 固定的分块策略 | 动态调整检索范围 |
| 适用场景 | 大规模文档检索 | 本地个人知识库、快速搭建 |

### 优势

- **更轻量简单**：不需要向量数据库，适合快速搭建本地个人知识库
- **检索更智能**：大模型参与分词、上下文匹配和决策，可智能调整
- **本质是 Agent + RAG**：代表了一种新的工作模式

### 当前不足

| 问题 | 说明 |
|------|------|
| 首次检索效率 | PDF 等特殊格式需先调用脚本转换，首次效率较低。建议预处理为纯文本 |
| 调用稳定性 | 多轮检索后 AI 可能忘记调用 Skill，丢失关键处理步骤（需从 Agent 客户端层面解决） |
| Token 消耗 | 检索过程由 AI 控制，未命中时会继续尝试，消耗更多 token |

## 七、为已有文档站创建专属 Skill

如果已有固定格式的文档站（如纯 Markdown 文档），可以通过 **Skill Creator** 自动生成专属的知识检索 Skill：

### 操作步骤

1. 在项目中加入 `skill-creator` Skill
2. 输入提示词描述需求：

```text
当前项目是一个文档站，包含多个 Markdown 文档。
我想创建一个专用于知识检索的 Skill，可以替代传统的 RAG，
用于当前文档站的知识检索。
基本思路：根据用户问题提取关键词 → 使用 grep 找到上下文 → 分析上下文
如果检索信息与问题不符，继续检索其他关键词，最大重试 5 次。
```

3. Skill Creator 自动生成适配当前文档站的 Skill

### 效果

- 自动生成的 Skill 包含针对当前文档站的最佳实践
- 因为是纯 Markdown 格式，结构非常简单（只有 skill.md）
- 检索速度快，答案准确

## 八、总结

该方案可以理解为：**不需要向量数据库、基于本地目录的渐进式检索 RAG**。

核心思想是将 Skill 的渐进式披露策略应用到知识检索场景，让 Agent 像人一样逐步缩小范围、精准定位答案，而不是一次性读取所有文件内容。这代表了从传统 RAG 向 **Agent-driven RAG** 演进的一个方向。
