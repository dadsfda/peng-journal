## 一、视频效果是怎么做的

### 为什么不用视频生成模型？

作者的技术讲解视频**不是用视频生成模型做的**，也没有用 NotebookLM，而是**用 Web Coding 写出来的网页**。

选择网页而非视频模型的原因：

| 方案 | 问题 |
|------|------|
| AI 视频生成模型 | 字体、配色、停留时间、帧级精确数字等无法精确控制，类似"抽卡"，稳定性差 |
| NotebookLM | 做不了动画演示效果，只能出静态图 |
| Remotion 框架 | 反而限制了模型发挥，不如直接让模型写代码自由 |
| **Web 网页** | 可控性强，改几行代码即可精确调整，成本更低、更稳定 |

### 视频效果展示

以一期视频为例（基于 Anthropic 最新文章生成）：
- 输入：一篇 Anthropic 发布的技术文章
- 输出：一个网页形式的知识讲解视频
- 特点：
  - 文章被拆成 **13 个章节**、**100+ 细粒度讲解步骤**
  - 每一步都有完整的视觉演示效果
  - 底部隐藏进度条，鼠标悬浮时出现
  - 支持任意跳转章节和步骤
  - 无页眉、页码、品牌标识，画面干净，看起来像视频而非网页

## 二、制作视频的四个关键步骤

### 步骤一：文章变口播稿

原始技术文章一般比较书面化（如"该工具旨在提供高效的解决方案"），需要改成：
- 短句、口语化
- 第二人称
- 像跟人聊天一样

### 步骤二：口播稿拆成开发计划/大纲

- 每段话对应一个具体的画面步骤
- 每几个步骤组成一个章节
- 每个章节聚焦一个话题
- 提前做好大纲是保持后续稳定性的关键

### 步骤三：每一步做视觉演示

- 不能直接把口播稿文字糊上去
- 要让网页用动态效果把抽象概念演示出来

### 步骤四：网页演示跟随口播稿节奏

- 关键演示步骤跟随口播稿节奏走
- 这样视频效果才显得自然

## 三、为什么需要 Skill（Harness）

### 问题：模型有能力，但不稳定

模型本身不缺能力，但直接跟 Agent 说"帮我做个视频网页"：
- 可能做得不错，但也可能跑偏
- 稿子和画面对不上
- 章节和音频数不一致
- 后面章节风格突然跟前面不搭

### 解决方案：用 Skill 驾驭过程

> 模型有能力，但你需要一套机制来驾驭这个过程——划定边界、设定检查点、自检和修复。这就是 Harness Engineering 需要负责的事情。

Skill 本身就是一份给 Agent 的操作手册：
- 告诉 Agent 什么时候该做什么
- 做到什么标准
- 哪些红线不能碰

Agent 加载 Skill 后按规则干活，不用每次重新复述规矩。

## 四、Skill 核心设计（Harness 六层拆解）

Skill 名称：**web video presentation**，托管在 garden skills 仓库。

### 1. 执行与编排层 —— 下一步该做什么

整个流程切成 **四个阶段**，中间卡了 **两个人工检查节点**：

```text
阶段一：内容编写
  ├── AI 产出口播稿 + 开发计划
  ├── 口播稿：决定信息描述方式和整体节奏
  └── 开发计划：决定每章做几步、每步屏幕上放什么
        ↓
  【人工检查节点 1】
  ├── 稿子和开发计划要不要改？
  ├── 用哪套主题？素材怎么准备？
  └── 后续章节逐章做还是并行做？
        ↓
阶段二：开发
  ├── 第一章开发完成 → 必须人工验收（提供基准参考）
  ├── 后续章节：可按顺序做，也可开多个子 Agent 并行写
  ├── 每章写完后逐项对照检查清单自检
  └── 全部过关才能交付
        ↓
  【人工检查节点 2：音频检查】
  ├── 是否需要自动合成音频？
  ├── 是 → 进入阶段三
  └── 否 → 跳到最后阶段（自己录音）
        ↓
阶段三：音频合成
  ├── 从口播稿对照网页步骤，提取音频合成清单
  └── 调用 TTS 合成音频
        ↓
阶段四：录屏
  ├── 浏览器打开网页
  ├── 开启音频自动播放
  └── 直接录屏 → 音频和画面天然对齐的成品视频
```

### 2. 上下文层 —— 模型能看到什么

链路横跨四个阶段，如果启动时把所有文档一股脑灌进去，模型注意力会被严重稀释。

**渐进式披露设计**：所有信息拆成多份文档，每份只在指定阶段读取：

| 文档 | 读取时机 |
|------|----------|
| 口播稿规范 | 第一阶段 |
| 章节开发指引 | 开发阶段 |
| 音频合成文档 | 音频合成阶段 |

好处：模型在任何时候面前摆的都是最需要的信息，不被无关内容干扰。

### 3. 状态与记忆层 —— 跨步骤保持连续性

最重要的记忆是**开发计划（outline.md）**：
- 一个项目可能有十几个章节、上百个步骤
- Agent 写到后面章节时，前面定过的结构、用户在检查点改过的方向可能已不在上下文中
- 开发计划把关键决定固定下来，成为开发阶段的持续记忆

开发阶段还强制让 Agent 同时读取三个文件：

| 文件 | 作用 |
|------|------|
| 开发计划（outline.md） | 整体结构和章节边界 |
| 口播稿（script.md） | 整体节奏——先讲什么后讲什么，画面必须跟着口播稿走 |
| 原文章 | 信息密度——口播稿通常更精简，画面里的数据、案例从原文补 |

三份文档各有分工，Agent 开发每个章节时同时参考，不容易出现"结构对了但画面空了"或"信息很多但节奏乱了"的问题。

本质上是一种**文件化的工作记忆**——把关键状态写进文件，需要时再读回来。

### 4. 工具层 —— 模型能做什么

核心就是让模型把 Agent 自带的**文件读写工具**用好。

解决多章节并行开发的冲突问题——严格的隔离机制：

- 每章必须是**独立文件夹**（物理隔离）
- 每章是**独立 CSS 前缀**（不互相抢类名）
- **主题 Token** 兜底视觉统一（字体、颜色、间距走全局变量）

即使每个 Agent 独立开发，也能保持视觉风格一致，各章节互不影响。

### 5. 约束与恢复层 —— 出错了怎么办

最常见的"出错"不是代码报错，而是**用户觉得不对**（节奏太快、动画太重等）。

**关键原则：反馈修复的最小切片**

- Agent 的本能反应：重做整章（重新生成成本不高）
- 问题：重做整章会把已经做对的部分也改掉
- 正确做法：
  1. 先定位问题在哪一层（节奏？视觉？内容？代码？）
  2. 只改最小的切片
  3. 不重做整章

### 6. 评估与观测层 —— 怎么知道做的对不对

对应 Anthropic 提出的**自评失真**问题：让写代码的 Agent 自己评价"这章写得怎么样"，结果大概率是"还不错"。

**解决方案：硬性的自检规则**

- 每个关键流程完成后，必须走"自检 → 修复 → 再汇报"流程
- 每个阶段都有完整的一套自检规则

最优方案（按优先级）：
1. **Agent Teams**：开一个独立的 Reviewer Agent，给它产出文件 + 对应清单，让它从零开始逐项检查
2. **Sub Agent**：次选方案
3. **当前 Agent 自查**：最次兜底，但也必须严格逐项，不允许目测一遍就放行

## 五、与工业级 Harness 的关系

> 回过头来把这个 Skill 的设计摊开来看，你会发现它和 Anthropic、OpenAI 的实践本质上没有区别，都是在搭建 Harness。只不过他们搭建的是工业级的运行系统，我们做的是一个 Skill 级别的协作协议。

**误区澄清**：做 Harness 不是非得从零做一个 Agent。能用一个 Skill 约束 Agent，把一个垂直的工作做好，也是在做 Harness。

## 六、实战演示

### 工具准备

| 工具 | 用途 |
|------|------|
| **Claude Code** | 核心执行 Agent（也支持 Cursor、Codex 等支持 Skill 的 Agent） |
| **MiniMax TokenPlan** | 国产模型，适配 Claude Code，性价比高，附带多模态套餐（图片、语音、视频） |
| **CC Switch** | 桌面配置工具，让 Claude Code 切换为 MiniMax 等自定义模型 |
| **MiniMax CLI** | 用于语音合成（TTS），TokenPlan 自带每天 9000 字语音合成额度 |
| **tmux**（可选） | 终端管理器，配合 Agent Teams 可视化多 Agent 并行工作 |
| **Agent Teams**（可选） | 多 Agent 协作，支持并行开发和质检 |

### Skill 安装

1. 访问 garden skills 的 GitHub 仓库
2. 下载 **web video presentation** Skill 安装包
3. 解压后复制到工作目录的 `.claude/skills/` 下
4. 启动 Claude Code，输入 `/web video` 能智能提示即配置成功

### 完整流程演示

以《一封邮件发出后的 600ms》文章为例：

#### 第一阶段：内容编写

1. 把原始文章丢给 Claude Code，使用 Skill 完成第一步
2. AI 编写**口播稿**（script.md）和**开发计划**（outline.md）
3. 开启独立 Reviewer Agent 进行质检（tmux 分屏展示）
4. 质检通过后主 Agent 根据评审结论更改，校对输出最终版本

输出文件：
- **script.md**：口播脚本，句子更短、节奏更快，像真人在聊天而非念文章
- **outline.md**：开发大纲，把脚本和原文拆成细粒度的章节和步骤，标注每步屏幕应出现的信息

#### 人工检查节点 1

Agent 向用户询问关键问题：
1. **稿子和开发计划要不要改？** 如果 AI 味重可以调整成自己讲话风格
2. **选什么主题？** Skill 定义了几套不同风格的主题，也会根据内容推荐
3. **素材怎么准备？** 手动提供还是 AI 自己绘制
4. **开发模式选择：**
   - 逐章确认（每章开发后人工验收）
   - 第一章确认后顺序完成
   - 第一章确认后并行开发（Sub Agent）

#### 第二阶段：开发

1. **第一章单独开发** → 人工验收（基准参考）
   - 确认页面密度、字体大小、动效节奏、信息呈现方式
   - 如有问题可继续调整
   - 第一章是后续所有章节的基准

2. **后续章节并行开发**（Agent Teams）
   - 最多同时并行跑 3 个 Agent 比较合适
   - 每个 Agent 拿到自己负责的章节大纲 + Skill 规范 + 第一章代码作为参考
   - 各写各的互不干扰
   - 每章完成后进入质检环节（需要能力较强的模型）

3. **整体验收**
   - 检查空白页、动画卡顿、步骤对不上、内容错位
   - 50 多步的项目中间某步出问题很正常，可让 Agent 修改

#### 阶段三：音频合成

1. 用 MiniMax CLI 把口播脚本批量合成为音频文件
2. 合成前先从所有章节抽出详细口播文本清单，检查错字漏句
3. 逐条合成音频
4. 遇到速率限制报错会记录错误文件重新合成，已生成的自动跳过，中途中断不用重来
5. 输出：每个章节一个子目录，每步对应一个音频文件，文件名与步骤编号一一对应

#### 阶段四：录屏

网页提供三种模式：

| 模式 | URL 参数 | 说明 |
|------|----------|------|
| 手动模式 | 默认 | 不播放音频，自由切换步骤，自己录音 |
| 音频播放模式 | `?audio=1` | 手动切换步骤，每步自动播放音频 |
| 自动模式 | `?auto=1` | 按空格后页面按音频节奏自动播放 |

选择适合自己的方式录制即可。

## 七、总结

> 表面上看我们讲的是一套文章变成视频的流程，但本质上它是一次 Harness 的具体实践。

**核心要点：**
- 模型能力已经很强了——Claude Code 能写代码，MiniMax 提供稳定的推理和语音合成能力
- 真正要关注的是：**怎么把这些能力稳定地编排起来，让 Agent 能稳定地完成**
- Skill 做的事情：把一次复杂的内容生产任务拆成**有流程、有状态、有检查点、有自检、有恢复机制**的工程系统

**Harness 的核心价值：**

> 把模型能力、工具能力和人的判断，组织成一条稳定可控的生产流程。

可以用类似的思路在自己的真实工作中实践。
